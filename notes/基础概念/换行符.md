# 换行符

文本里按 Enter 换行时，文件里其实写的是控制字符，不是肉眼能看到的字。不同操作系统约定了不同的控制字符，所以同样一份文本，在 Windows 和 macOS/Linux 之间拷来拷去时，经常出现「换行对不上」的问题。

## 为什么不同系统中的换行符不一样？

这套差异来自早期打字机 / 电传打字机：

- **CR（Carriage Return，回车）**：把「打印头」拉回行首，相当于光标回到这一行开头。
- **LF（Line Feed，换行）**：把纸往上走一行，相当于光标往下一行。

要真正开始写下一行，机械上需要两步：先回行首，再走纸。后来操作系统各自简化了约定：

| 系统 | 选择 | 原因（简化理解） |
| --- | --- | --- |
| Windows / 早期 DOS | `CRLF`（两步都保留） | 继承 CP/M / DOS 的电传机习惯 |
| Unix / Linux / 现代 macOS | `LF`（只保留换行） | Unix 把「换行」当成一个动作就够了 |
| 很老的 Mac OS（OS X 之前） | `CR`（只保留回车） | 另一套简化，现在基本遇不到 |

所以：**不是 UTF-8 编码不同，而是「这一行结束」用了不同的控制字节。**

## 不同系统中换行符分别是什么？

在 UTF-8 / ASCII 里，它们就是固定的字节：

| 名称 | 含义 | 字节（十六进制） | 常见系统 |
| --- | --- | --- | --- |
| `LF` | Line Feed，换行 | `0A` | macOS、Linux、Git 仓库里通常用这个 |
| `CR` | Carriage Return，回车 | `0D` | 旧 Mac OS |
| `CRLF` | 回车 + 换行 | `0D 0A` | Windows |

### macOS / Linux

`LF`，字节 `0A`。

```text
hello\nworld
```

文件里实际是：`h e l l o 0A w o r l d`

### Windows

`CRLF`，字节 `0D 0A`。

```text
hello\r\nworld
```

文件里实际是：`h e l l o 0D 0A w o r l d`

在编辑器里打开「显示空白字符 / 换行符」时，常见显示是：

- `LF` → `¬` 或 `↓`
- `CRLF` → `↵` 或 `CRLF`

:::tip
同一份源码里如果混用 `LF` 和 `CRLF`，Git diff 会看起来「整文件都改了」，其实可能只是换行符变了。
:::

## Git 过程中换行符注意事项

Git 的默认策略是：**仓库里尽量统一成 `LF`，工作区可以按本机习惯显示。**

### 容易踩的坑

1. Windows 上 clone 后，Git 可能把 `LF` 转成 `CRLF`，提交时再转回 `LF`。
2. 如果有人关了转换、有人开了转换，同一文件会变成「每次提交都改换行」。
3. 编辑器（VS Code / Cursor）如果「自动检测」失败，也可能把文件存成另一种换行。

### 推荐做法

**1. 仓库根目录放 `.gitattributes`（比本机 Git 配置更可靠）**

```gitattributes
* text=auto eol=lf
```

含义：文本文件进仓库时统一成 `LF`，不把换行风格交给每个人的本机设置。

二进制文件不要当文本转，可以再加：

```gitattributes
*.png binary
*.jpg binary
*.ico binary
```

**2. 本机 `core.autocrlf`（辅助，不要只靠它）**

| 系统 | 建议 | 行为 |
| --- | --- | --- |
| Windows | `true` | 检出时 `LF → CRLF`，提交时 `CRLF → LF` |
| macOS / Linux | `input` | 提交时把 `CRLF` 转成 `LF`，检出不乱转 |

```bash
# Windows
git config --global core.autocrlf true

# macOS / Linux
git config --global core.autocrlf input
```

**3. 编辑器也统一**

Cursor / VS Code 右下角可以看到 `LF` 或 `CRLF`。团队项目建议固定为 `LF`：

```json
{
  "files.eol": "\n"
}
```

### 已经乱了怎么查、怎么修

看某个文件现在是什么换行：

```bash
git ls-files --eol
```

输出里 `i/` 是仓库里的，`w/` 是工作区的。理想情况文本文件是 `i/lf`。

如果只是换行符脏了、内容没改，可以按仓库规则重新检出（先确认没有未提交的有效改动）：

```bash
git add --renormalize .
```

:::warning
不要为了「消掉 Git 的 CRLF 警告」去把整个仓库改成 `core.autocrlf false` 还继续混用。警告本身不可怕，混用才可怕。
:::
